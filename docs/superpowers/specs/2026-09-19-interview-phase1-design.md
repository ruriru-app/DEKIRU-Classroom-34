# Interview 実装① 設計案

## 目的と今回の境界

管理者が既存のGames作成・管理画面でInterviewプリセットを作り、教師はUnitのActivitiesから開いて名簿を設定し、URLで児童へ配信できるようにする。

今回作るものはプリセット管理、Unitへの紐付け、教師の準備画面、端末内名簿管理、URL配信、受信確認用の仮画面まで。児童の文章作り／Interview Sheet本画面、回答操作、音声、PDF、Classroom提出、サブスクリプション、認証、パスワード画面は作らない。

## 合意した保存・公開方針

- プリセットは作成したブラウザ内に保存する。保存は一般公開を意味しない。
- 本ページへの収録はユーザーがこの会話で依頼したプリセットだけ実施する。自動アップロードはしない。
- 今回はColorsを作者用のテストデータとして作成し、同じブラウザで一連の流れを確認する。一般教師向け公開カタログには自動追加しない。
- 将来の収録用に、名簿を含まないプリセットJSONを取り出せるようにする。公開用カタログの初期値は空にする。
- Gamesの既存作者用画面には現在認証がない。今回も安全な管理者認証があるとは表示しない。将来の認証は管理入口と保存先を差し替えられる境界にするが、課金システム自体は設計・実装しない。

## 既存実装と再利用

- `games_site/index.html` のCreate GamesへInterview作成対象と管理リストを追加。ROULETTE RACEの画面・保存データは維持する。Interview専用の別管理サイトは作らない。
- `games_site/creator.js` のカード選択とUnitチェック欄の構成を踏襲。共通化は必要な小さな部品に限定する。
- 既存カードカタログのIDで参照し、画像や単語データを重複登録しない。配信用には安定したIDを使用し、カタログの配列順には依存しない。
- `grade34_site/card-share.js` のURL／QR表示、コピー、試す操作を再利用する。
- `grade34_site/card-set.js` とGamesのURL共有の方式（JSONをURL安全な形式に変換し、ハッシュへ格納）を踏襲。必要な汎用変換部分のみ共通化し、既存URLの形式と復号動作は維持する。
- 既存Gamesの保存は `dekiru-created-games-v1` にROULETTE専用の正規化があるため、この配列へ異種データを混ぜない。Interviewは専用ストアを同じ管理UIから扱う。
- 調査した範囲では共通名簿保存機構がないため、小さな独立した名簿ストアを追加する。

## 画面と導線

### 作者

Create Games → Interview → 名前、表示タイトル、説明、質問テンプレート、カード、回答エリア、対象教科書／Unitを設定 → 保存。

保存リストから編集・削除・教師画面で試す・公開依頼用JSON取得ができる。通常のGamesプレイ一覧にはInterviewを追加しない。保存失敗時は成功表示しない。

教科書IDは既存の `lt1 / lt2 / nh5 / nh6`、Unit範囲はそれぞれ1～9／1～9／1～8／1～8を検証する。複数Unitへの割り当てと、同一Unitへの複数プリセットを許可する。

### 教師

Unit → Activities → 対象Interview → 内容の読み取り専用プレビュー → 名簿選択／貼り付け → 確認 → 配信。

Grade 3&4のUnit内ActivitiesとActivities表示導線へ同じ一覧取得処理を接続する。Grade 5&6はUnitが準備中のため、Interviewが割り当てられたUnitに限って最小限のActivities欄を追加し、他教材を完成済みに見せない。

質問文・カード・回答エリアの編集は作者側のみ。教師の準備画面は共通化し、どちらの学年からも利用できるようにする。英語はAndika、戻るボタンは既存の共通SVGと全画面解除ルールに従う。

### 児童の仮画面

URLを復号し、「受信確認用・本画面は準備中」と表示する。タイトル、質問テンプレート、カード数、回答エリア、名簿人数を確認可能にする。名前を分類する操作や児童の活動結果生成は追加しない。

## データ契約（version 1）

### InterviewPreset

- `version: 1`, `type: 'interview'`, `id`: 安定したID
- `name`, `title`, `description`
- `assignedUnits`: `{ bookId, unit }` の配列
- `question`: `{ template, slots }`
- `question.template`: 最初は `Do you like (P)?`。スロットなしの固定文も許可する。
- `question.slots`: `{ id: 'P', type: 'picture-card', cardIds: [...] }` の配列。今回は0または1スロットを扱い、未定義のスロットや複数スロットは明示的にエラーにする。将来の拡張を黙って誤解釈しない。
- `cardIds`: 使用可能な既存Picture CardのID配列
- `answerAreas`: `{ id, label, order, speechText? }` の配列。YES/NO固定ロジックを持たず、順序・ID重複・空欄を検証する。
- `createdAt`, `updatedAt`

カードIDと回答エリアIDは編集で並べ替えても維持する。質問文にはHTMLではなく文字列を保存し、安全なテキストとして表示する。

### ClassRoster

- `version: 1`, `id`, `className`, `createdAt`, `updatedAt`
- `students`: `{ id, number?, name }` の配列

名前のみの改行区切りと、番号＋名前のタブ区切りを受け付ける。例示の全角空白区切りの番号にも対応する。氏名中の空白は保持する。空行は除き、人数と一覧を保存前に確認できる。重複名は別児童として扱い、番号の重複は警告する。編集時は既存児童IDを維持し、削除は確認を挟む。35人程度を主対象とし、入力上限と保存容量エラーを明示する。

新規作成・保存・保存済みクラス選択・編集・削除を提供する。名簿は同一端末・同一ブラウザ・同一オリジンのlocalStorageに保存し、別端末へ自動同期されないことを表示する。

### InterviewDelivery

- `version: 1`, `type: 'interview-delivery'`, `deliveryId`, `issuedAt`
- `presetId` と、発行時点の `preset` スナップショット
- `roster`: 発行時点の名簿スナップショット

発行後に教師がプリセットや名簿を変更しても、既に渡したURLの内容は変わらない。受信端末に作者のlocalStorageは不要。カード画像本体はURLに含めず、既存IDを配信先のカタログで解決する。存在しないID・不正なバージョン・過大なデータは理由を表示して拒否する。

今後の活動結果は下記の契約を用いて表現できる。今回は結果保存・提出機能を実装しない。

## 第2・第3工程から引き継ぐ設計条件（今回実装しない）

### 児童の進捗・結果

- `version`, `deliveryId`, `attemptId`, `presetId`: 配信と活動の識別子。別の配信・次の活動の結果を混ぜない。
- `phase`: 文章作り／Interview Sheet／結果確認を区別する。
- `selectedCardId`, `completedQuestion`: 選んだカードと完成文。質問は固定部分・Picture Cardスロット・句読点へ分解可能なテンプレートから組み立てる。
- `assignments`: 名簿の児童IDをキー、回答エリアIDまたは `null` を値とする。各児童は常に1か所だけに所属する。名前を直接キーにせず、同名でも別人として扱う。
- `respondent`: 操作している児童本人の `{ className, number, name, rosterStudentId? }`。インタビュー相手の名簿とは分離し、本人が明示的に選択または入力する。端末・名簿・回答内容から本人を推測しない。
- `startedAt`, `finishedAt`, `updatedAt`, `timeZone`: 端末日時で記録する。配信日時 `issuedAt` と活動日時を混同しない。

実施人数は有効な回答エリアIDを持つ名簿児童の数、未実施人数は未配置の名簿児童の数から算出する。画面内のタイル数やDOMから集計しない。氏名を複製した回答リストや人数の二重保存を避け、配信スナップショットと配置マップを参照する。

### 第2工程の操作・保持条件

文章作りでカード未選択なら開始できない。固定文だけのプリセットも扱える。Sheetはタイトルと既存発音調整、左端スピーカー付きの質問カード、可変個数の回答エリア、未実施の名前タイルの順とする。35人程度を想定し、Chromebook／タブレットで可能な限り1画面に収める。

操作は「名前を選択→移動先を選択」に統一する。回答エリア全体をタップ対象とし、未実施も移動先にできる。回答がある状態で質問を変更する場合は確認後に回答を初期化し、取り消した場合は質問・回答とも維持する。再描画・再読込に備えて進捗を端末保存する。

### 第3工程の成果物・失敗時の保持条件

活動終了は通常操作と分離し、結果確認→本人情報確認→提出用PDFの生成・端末保存へ進む。PDFは活動画面の単なるスクリーンショットではなく、教師向けの整形レイアウトとする。ブラウザ内生成を優先し、具体的なPDFライブラリや方式は第3工程の着手時に決定する。

PDFには本人の組・番号・名前、Interviewタイトル、完成文、選択カード、各回答エリア名と配置済みの名前、実施／未実施人数、活動日時を含める。2～4分類など可変個数に対応する。画像埋め込みに問題があっても英語と結果の出力を優先する。ファイル名は本人を識別できる形にし、使用不可文字を除く。

終了・PDF生成・保存の失敗や再生成では元データを消さない。Sheetへ戻って修正可能とし、明示的な確認付きリセットまで結果を保持する。リセットでは選択カード・完成文・配置・本人情報・活動時刻を初期化し、受信したプリセットと名簿は残す。

PDF生成はGoogle Classroomへの提出完了を意味しない。「保存して、先生の指定した課題へ添付する」と短く案内する。Classroom API、自動ログイン、自動アップロード、自動提出、採点は追加しない。アプリから名簿・結果を外部サーバーへ送信しない。PDFやURLにはクラスメンバー名が含まれるため授業内での扱いを明示する。

### 工程の停止条件

第1工程は教師配信と受信仮画面までで停止。第2工程は児童の2画面・操作・進捗保持を確認して停止。第3工程は結果確認・PDF保存までを確認して停止する。各工程の完了と次工程への明示的な指示を待ち、全体仕様を受け取ったことだけで後続工程を始めない。

## URL配信と名簿の扱い

配信用データをURLのハッシュに持たせる。PINや新規サーバーは使わない。圧縮可能なら既存と同じ方式で短くし、復号時にサイズ上限を設ける。QR容量を超えた場合もURLコピーは利用可能とする。

URLには名簿が含まれるため、生成前に「このURLを知る人は名簿を閲覧できます。クラス内だけで共有してください」と明示し確認を求める。暗号化やアクセス制限があるとは説明しない。名簿を公開カタログ・Git・更新情報・ログへ保存しない。受信画面は外部解析や不要な外部通信を追加しない。

`file:` で開いた場合は端末間共有の保証がないため、既存と同じ配信注意を表示する。端末をまたぐ試験は同一オリジンのローカルHTTP環境または承認済み公開環境で行う。

## Colorsテストプリセット

作者画面の「Colorsサンプルを作成」から通常の編集フォームへ読み込む。質問 `Do you like (P)?`、既存のred／blue／green／yellow／pink／orange／purple／black／whiteカード、回答YES／NOを使用する。

対象は既存の `Let’s Try! 1 Unit 4 — I like blue.` とし、保存時に割り当てを確認できる。初回ページ表示だけで保存・公開はしない。確認用名簿には架空名を使用する。

## 検証と完成条件

1. 作者画面で作成・保存・再読込・編集・削除でき、ROULETTEの保存内容が変わらない。
2. カード選択、テンプレート、可変個数の回答エリア、複数Unit割り当てを保存できる。
3. InterviewはActivitiesにだけ現れ、Games（みんなで／個別）には現れない。
4. 名前のみ／番号付き貼り付け、35人名簿、重複名、空行、保存・編集・削除、容量エラーを試験する。
5. 別ブラウザコンテキストで配信URLを開き、作者の保存状態なしで内容を復元できる。
6. 配信後の編集が発行済みURLに影響せず、不正URLは安全に失敗する。
7. 共通SVG、Andika、URLコピー、QR失敗時の代替、戻る操作を確認する。
8. 既存のGames、Unit、Picture Cards、発音練習、文で話そう、既存Activitiesの回帰テストを実施する。

変更ファイル・データ構造・再利用箇所・試験結果・次工程の注意点を報告し、ここで停止する。公開カタログへの収録や児童画面本実装を勝手に進めない。
